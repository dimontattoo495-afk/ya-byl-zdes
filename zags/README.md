# Виртуальный ЗАГС — тестовая интеграция

Ветка: `zags-integration`. Рабочая `main` не меняется.

## Реализовано
- /zags/index.html — интерфейс и демонстрация.
- Подключение Supabase из `../config.js` (публичный ключ).
- Email OTP через `signInWithOtp` и `verifyOtp`.
- Вход перед приватными операциями и перед проверкой приглашения.
- Серверные вызовы `zags_action` для работы с парами.
- `paymentsEnabled:false`: UI не инициирует оплату.

## Не считать запуском в эксплуатацию
- Файл находится только в отдельной ветке; GitHub Pages публикует рабочую ветку.
- Реальные платежи отключены и не должны включаться до отдельных тестов.
- Публичные страницы сейчас требуют входа, потому что у роли `anon` нет EXECUTE для `zags_action`.
- Необходимо провести ручной тест с ДВУМЯ независимыми email-аккаунтами, регистрации пары, приглашения, принятия и чтения.
- Необходимо проверить SQL-валидаторы входных данных и лимиты длины, RLS и права SECURITY DEFINER на продакшен-базе.
- Проверить полную авторизацию через OTP: при реальном новом аккаунте 13.10.2026 Supabase прислал 8 цифр; форма принимает 6–8 цифр. Не сохранять одноразовые коды в GitHub или логах.
- Не передавать клиентскому коду service-role ключи, токены платежей или SMTP-пароли.

## Почтовые шаблоны — обязательный этап перед реальными регистрациями

В Supabase → Authentication → Emails → Templates нужны ДВА шаблона с кодом:

1. **Confirm sign up** — для новых email, которые ранее не регистрировались. Тема: `Я был здесь | Подтверждение почты`. Содержимое взять из `zags/templates/confirm-signup.html`.
2. **Magic link or OTP** — для входа ранее зарегистрированных пользователей. Тема: `Я был здесь | Код входа`. Содержимое взять из `zags/templates/magic-link-otp.html`.

В обоих случаях HTML использует переменную `{{ .Token }}`, а не `{{ .ConfirmationURL }}`. Шаблон Confirm sign up сохранён пользователем в Supabase Dashboard и реальная доставка подтверждена 13.10.2026. Шаблон Magic link or OTP для существующих аккаунтов требует отдельной проверки.

Проверить вручную с двумя разными настоящими email: 1) код создания нового аккаунта, 2) код повторного входа, 3) создание заявления, 4) открытие приглашения только после авторизации партнёра, 5) согласие с другого аккаунта, 6) отсутствие оплаты.

## Что пока не автоматизировано

- Полный сценарий в реальном Supabase пройден 13.10.2026: новый Gmail аккаунт, вход по коду, создание одного заявления; второй участник с отдельным Яндекс-аккаунтом открыл ссылку, вошёл по OTP и принял приглашение. В базе подтверждена одна пара с двумя участниками, без оплаты. Для входа использовались локальные HTML-файлы: такую ссылку нельзя раздавать пользователям. При изменении основной страницы понадобятся повторные проверки.
- Включение публичного чтения семейных страниц без входа — для этого нужен отдельный безопасный read-only endpoint.
- Отдельная проверка SQL функции `zags_action`: длина строк и валидность значений, политика по хранению персональных данных, публичные статусы, разграничение прав `SECURITY DEFINER`.
- Проверка в браузере после фактической публикации. Выпуск в `main` без владельца не производить.
- В тестовой версии платежи заблокированы. После принятия приглашения интерфейс не должен побуждать к оплате. Соответствующий браузерный тест добавлен.
